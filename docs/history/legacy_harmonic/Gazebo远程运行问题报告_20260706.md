# Gazebo 远程运行问题报告（历史）

> **历史资料，禁止作为当前操作手册。** 本文基于早期本地 Gazebo Harmonic / 远程桌面方案；当前官方 SimEnv 接入请使用 `docs/guidebook/官方SimEnv平台环境使用手册.md`。

更新时间：2026-06-16  
适用对象：**全队成员**（平台组、集成组必读）  
目标机器：`hxbl`（Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonic 8.11 + NVIDIA RTX A6000）

> 本文档说明在主力机 **GNOME Remote Desktop（RDP）** 环境下 Gazebo 无法稳定显示 GUI 的原因，以及可行的替代运行方式。  
> 与远程桌面连接步骤见 [主力机与远程接入使用指南（临时旧版）](../../guidebook/主力机与远程接入使用指南（临时旧版）.md)。

## 1. 问题现象（成员反馈）

| 现象 | 描述 |
| --- | --- |
| **期望行为** | 运行仿真代码后，弹出 Gazebo 3D 图形界面 |
| **实际行为** | 图形界面不出现；或远程桌面（RDP）崩溃、断连、卡死 |
| **可行变通** | 使用 headless 模式（`gz sim -s` 或 `headless:=true`）可正常运行仿真 |
| **影响范围** | 在 RDP 远程桌面内启动 **带 GUI** 的 Gazebo 时复现；与具体 Linux 账号无本质区别 |

平台组 `hazard_platform` 账号历史命令显示，曾多次执行：

```bash
ros2 launch hazardwalker_platform gazebo_minimal.launch.py
```

该 launch 默认 `headless:=false`，会启动带 GUI 的 `gz sim -r`，与上述现象一致。

## 2. 测试与复现记录

测试在 **`hazard_test`** 账号下进行，采用隔离方式（不重启共享服务、不清理他人会话）。

| 测试项 | 命令 / 条件 | 结果 |
| --- | --- | --- |
| Headless 仿真 | `gz sim -s -r empty.sdf` | **通过**，世界正常加载 |
| GUI 仿真（RDP 会话环境） | `gz sim -r empty.sdf` | **失败**，EGL/OpenGL 初始化错误 |
| 测试后 RDP 会话 | `hazard_test` gnome-shell / grd | **正常** |
| 其他组员会话 | platform / nav / perception | **未受影响** |

关键错误日志摘录：

```text
libEGL warning: pci id for fd: 10de:2230, driver (null)
libEGL warning: egl: failed to create dri2 screen
[GUI] [Err] Failed to create OpenGL context
qt.qpa.xcb: could not connect to display
Aborted / Segmentation fault
```

系统日志（`dmesg`）中反复出现：

```text
[drm:nv_drm_master_set] Failed to grab modeset ownership
```

表明多路 RDP 并发时，GPU 显示资源存在竞争。

---

## 3. 根因分析

### 3.1 直接原因：RDP 嵌套图形会话无法支撑 Gazebo GUI

主力机远程桌面采用 **GNOME Remote Desktop（GRD）**，每个 Linux 用户对应独立的 **Wayland + Xwayland** 嵌套会话，并非直连 GPU 的本地物理桌面。

在此环境中启动 `gz sim -r`（带 GUI）时，Gazebo 依赖 **Qt + Ogre2 + EGL/OpenGL** 创建 3D 渲染窗口。嵌套会话中 NVIDIA EGL 常无法正确加载（`driver (null)`），导致 OpenGL 上下文创建失败，进程 abort 或 segfault。

**结论**：Gazebo **仿真引擎（server）正常**；失败的是 **GUI 渲染层**，与 RDP 图形栈不兼容。

### 3.2 系统层原因：多路 RDP 争夺 GPU 显示资源

`nvidia-smi` 显示多路 RDP 会话各自占用 gnome-shell、gnome-remote-desktop-daemon、Xwayland 等图形进程显存。多用户同时远程桌面时，GPU modeset 所有权竞争加剧，进一步降低在 RDP 内启动 3D 应用的成功率。历史上曾出现 `gnome-shell crashed with signal 11` 记录。

测试时 GPU 状态为 **`Disp.A Off`**（显示输出未激活）。在无物理显示器或 HDMI 欺骗器时，NVIDIA 显示管线可能处于未完整初始化状态，会加剧 EGL/OpenGL 在嵌套会话中的失败概率；但这 **不是** 唯一根因——即便激活显示输出，**RDP 嵌套会话内开 Gazebo GUI 仍不可靠**（见第 6 节）。

### 3.3 触发路径：Launch 默认启动 GUI 模式

`gazebo_minimal.launch.py`（`feature/platform` 分支）中：

- `headless` 参数默认值为 `false`
- 非 headless 时执行：`gz sim -r -v 2 <world_file>`（强制 GUI）
- headless 时执行：`gz sim -s -r -v 2 <world_file>`（仅 server）

成员若直接运行 launch 而不传参，会默认走 **在 RDP 内必然失败** 的 GUI 路径。

### 3.4 已排除项

| 项目 | 结论 |
| --- | --- |
| Gazebo 安装 / 版本 | 正常（Harmonic 8.11.0） |
| Headless 仿真 | 正常 |
| 用户组 `video` / `render` | 已配置 |
| NVIDIA 驱动 / GPU 计算 | 535 驱动正常，计算无异常 |
| 「Gazebo 软件损坏」 | 否，属运行环境与用法问题 |

### 3.5 问题本质（一句话）

> **不是 Gazebo 坏了，而是「在 GRD 远程桌面里开 Gazebo 原生 3D GUI」与当前 hxbl 图形架构不兼容。**  
> 仿真（物理、传感器、ros_gz_bridge）可照常使用；应避免在 RDP 会话内启动 GUI 进程。

## 4. 可行解决方案

按 **推荐优先级** 排列。

### 4.1 方案一：Headless 运行（立即生效，推荐默认）

**适用**：全队日常仿真、算法联调、集成验证。

```bash
# 方式 A：launch 参数
ros2 launch hazardwalker_platform gazebo_minimal.launch.py headless:=true

# 方式 B：命令行
gz sim -s -r <world.sdf> -v 2
```

| 优点 | 缺点 |
| --- | --- |
| 已验证稳定，不导致 RDP 崩溃 | 无 Gazebo 3D 窗口 |
| 与 ros_gz_bridge、算法节点完全兼容 | 需配合 RViz 或其他方式查看可视化 |
| 零基础设施改动 | — |

**建议**：将 `gazebo_minimal.launch.py` 的 `headless` 默认值改为 `true`，避免在主力机环境误开 GUI。

---

### 4.2 方案二：Gazebo Server / GUI 分离（需要完整 3D 界面时首选）

**适用**：需要 Gazebo 原生 3D 编辑器、场景树、完整仿真视图。

**架构**：

```text
hxbl（仿真 server）              队员本机（GUI client）
─────────────────────           ─────────────────────
gz sim -s -r world.sdf      ←→   gz sim -g
headless:=true                   本机 GPU 渲染窗口
ros_gz_bridge + 算法节点            经 gz-transport 连接
```

**主力机**：

```bash
export GZ_PARTITION=hazardwalker_platform   # 每组使用不同 partition，避免串扰
export ROS_DOMAIN_ID=<本组 ID>

ros2 launch hazardwalker_platform gazebo_minimal.launch.py headless:=true
```

**队员本机**（需安装 Gazebo Harmonic 8.x，仓库与世界文件版本与 hxbl 一致）：

```bash
export GZ_PARTITION=hazardwalker_platform   # 与服务器相同
export GZ_IP=<本机 Tailscale 或局域网 IP>
export GZ_RELAY=100.102.91.31              # hxbl Tailscale IP（跨网时通常需要）

gz sim -g -v 2
```

本机需能访问同版本的 `worlds/`、`models/`（git 同步即可）。

| 优点 | 缺点 |
| --- | --- |
| 完整 Gazebo GUI，仿真仍在 hxbl | 本机需安装 Gazebo |
| 不占用 RDP 的 OpenGL | 需配置 `GZ_PARTITION` / `GZ_IP` / `GZ_RELAY` |
| 不改变现有 RDP 服务 | 跨网时需排查 gz-transport 连通性与防火墙 |

参考：[Gazebo Transport 环境变量](https://gazebosim.org/api/transport/14/envvars.html)

---

### 4.3 方案三：Headless Gazebo + RViz2 可视化

**适用**：查看机器人位姿、激光、点云、相机等，不需要 Gazebo 编辑器。

```bash
ros2 launch hazardwalker_platform gazebo_minimal.launch.py headless:=true

# 另开终端（RDP 内通常可用）
rviz2
```

通过 `ros_gz_bridge` 订阅 `/hw/*`、TF、传感器话题。

| 优点 | 缺点 |
| --- | --- |
| 无需本机安装 Gazebo | 非完整 Gazebo 场景视图 |
| RViz 在 RDP 中通常比 Gazebo GUI 稳定 | 依赖 bridge 配置完整性 |

---

### 4.4 方案四：Headless Rendering（离屏 GPU 渲染）

**适用**：需要 GPU 渲染相机图像，但不需要 GUI 窗口。

```bash
gz sim -s -r <world.sdf> --headless-rendering
```

渲染结果经 bridge 发布，在 RViz 或算法节点中消费。

| 优点 | 缺点 |
| --- | --- |
| 相机类传感器可走 GPU 离屏渲染 | 在 hxbl 多路 RDP 下 EGL 仍有不确定性，需单独验证 |
| 无 Qt GUI 窗口 | 不能替代 Gazebo 编辑器 |

---

### 4.5 方案五：VirtualGL + VNC（备选，见第 5 节详述）

**适用**：少数人必须在服务器侧看到 3D 窗口，且不愿在本机安装 Gazebo。  
**建议**：仅在前述方案无法满足时评估，不作为全队默认方案。

---

### 4.6 方案六：实体显示器 / 本地控制台会话（见第 6 节详述）

**适用**：队员能**到机房现场**操作 hxbl，或平台组需频繁在服务器本机调试 Gazebo 场景。  
**结论摘要**：

| 使用方式 | 能否解决 Gazebo GUI |
| --- | --- |
| 接显示器，在 **本机 GDM 登录** 的桌面里跑 `gz sim -r` | **可以**（推荐在机房本地使用） |
| 仅接显示器，队员仍通过 **RDP 远程** 开 Gazebo GUI | **不可以**（根因未变） |
| 接 **HDMI 欺骗器**（无真实屏幕），指望 RDP 内可用 GUI | **基本不可以**；仅有助于 GPU 显示管线初始化 |

**建议**：作为机房现场调试的补充手段，**不替代** headless 与本机 `gz sim -g` 的远程工作流。

## 5. VirtualGL + VNC 补充说明

本节单独说明 VirtualGL + TurboVNC（或类似组合）的优劣，以及与现有 GRD/RDP 的关系，供运维与队长决策参考。

### 5.1 方案原理简述

```text
                    ┌─────────────────────────────────────┐
  队员 VNC 客户端 ──►│ TurboVNC Server（独立 X11 会话）      │
                    │         │                           │
                    │         ▼                           │
                    │   VirtualGL 拦截 OpenGL 调用          │
                    │         │                           │
                    │         ▼                           │
                    │   NVIDIA GPU（ GLX/EGL 硬件渲染）    │
                    │         │                           │
                    │         ▼                           │
                    │   帧缓冲回传 ──► VNC 编码 ──► 客户端  │
                    └─────────────────────────────────────┘

  并行存在、互不替换：
  ┌─────────────────────────────────────┐
  │ GRD/RDP :3389（现有，全队默认）       │
  │ GNOME Wayland + 每用户独立会话        │
  └─────────────────────────────────────┘
```

VirtualGL 将 OpenGL 应用重定向到 NVIDIA GPU 渲染，再通过 VNC 把画面编码传给客户端。理论上可在远程看到完整 3D 窗口，且不走 GRD 的嵌套 Wayland 路径。

### 5.2 优势

| 优势 | 说明 |
| --- | --- |
| **可在远程看到完整 OpenGL/3D 窗口** | Gazebo GUI、部分 RViz 重负载场景等，不必在本机安装 Gazebo |
| **与 GRD 服务可并存** | VNC 通常使用 5900+ 端口，RDP 使用 3389；安装 VirtualGL/TurboVNC **不会自动卸载或停用** `gnome-remote-desktop` |
| **统一在服务器侧运行** | 世界文件、模型、依赖均在 hxbl，无需队员本机同步 Gazebo 版本 |
| **可绑定独立 X Display** | 若配置为 `:2`、`:3` 等独立会话，与 GDM `:0` 逻辑分离，降低「劫持系统桌面」风险 |
| **对无本地 GPU 的成员友好** | 使用轻薄本、Windows 且无 Gazebo 安装条件的成员，仍可能通过 VNC 查看 3D |
| **成熟方案** | HPC、实验室服务器上长期用于远程 OpenGL，文档与案例较多 |

### 5.3 问题与风险

| 问题 / 风险 | 说明 |
| --- | --- |
| **与现有 RDP 争用 GPU** | hxbl 上多路 GRD 已占用 gnome-shell、grd 编码器及显存；再开 VirtualGL 3D 会话会加剧 GPU 负载，可能引发 RDP 卡顿、掉帧、gnome-shell 崩溃（日志中已有 signal 11 先例） |
| **`nv_drm_master_set` 竞争** | 多显示会话同时请求 NVIDIA modeset 时，已观测到 `Failed to grab modeset ownership`；新增 VNC+X 会话可能加重该问题 |
| **配置不当可影响系统图形** | VirtualGL 若错误绑定 GDM 使用的 `:0` 或系统主显示，可能干扰本地/登录管理器，导致运维事故 |
| **双轨远程访问** | 队员需区分：日常开发走 RDP，看 Gazebo 3D 走 VNC；增加培训成本与文档维护量 |
| **安全与网络** | 需额外开放 VNC 端口；若对公网暴露风险高于 RDP，建议仅 Tailscale 内网可达 |
| **会话管理复杂** | 每用户独立 VNC display、启动/停止脚本、异常退出清理；与现有 `loginctl` / GRD 会话清理流程并列 |
| **性能与体验** | VNC 编码 3D 画面延迟通常高于本机 `gz sim -g`；复杂场景可能卡顿，交互体验不如本地 GUI |
| **运维与排障成本高** | NVIDIA 驱动升级、内核更新后 VirtualGL 可能需重新适配；故障面大于 headless + 分离 GUI |
| **不能根治 GRD 内开 Gazebo 的问题** | VirtualGL 是 **另开通道**，不是给现有 RDP 会话「打补丁」；在 RDP 终端里直接 `gz sim -r` 仍然不行 |
| **无物理显示器时的额外配置** | `nvidia-smi` 显示 `Disp.A Off` 时，可能需要 dummy HDMI、nvidia-xconfig 或特定 EGL 配置，部署前需验证 |
| **与 GRD H.264 硬编冲突可能** | 日志中 grd 已有 `[HWAccel.CUDA] Failed to load AVC utils module`；GPU 同时承担编码与 VirtualGL 渲染时，资源调度更紧张 |

### 5.4 与现有 GRD/RDP 的影响关系

| 维度 | 是否受影响 | 说明 |
| --- | --- | --- |
| RDP 服务是否被替换 | **否** | 默认并存，需主动切换客户端 |
| RDP 端口 / 账号体系 | **否** | 除非刻意改动防火墙或统一入口 |
| RDP 稳定性（间接） | **可能** | GPU/显存争用时，现有远程桌面可能更卡或更易崩 |
| 队员使用习惯 | **是** | 需学习第二套连接方式 |
| 运维工作量 | **是** | 安装、配置、监控、回滚均需额外投入 |

### 5.5 若未来部署 VirtualGL + VNC 的最低风险原则

1. **不修改、不替换现有 GRD 配置**；全队默认仍用 RDP。  
2. VirtualGL 使用 **独立 X display**（如 `:2`），**不劫持** GDM `:0`。  
3. **仅对确有 3D GUI 需求的账号** 开通 VNC，不全队迁移。  
4. VNC 端口 **仅 Tailscale 可达**，不对公网跳板开放。  
5. 制定回滚方案：停用 vncserver 单元即可恢复现状，无需动 GRD。  
6. 部署前在 `hazard_test` 单账号试点，观察对同机其他 RDP 会话的影响。

### 5.6 与其他方案对比（VirtualGL 定位）

| 维度 | Headless + 本机 `gz sim -g` | VirtualGL + VNC |
| --- | --- | --- |
| 3D 完整度 | 完整 Gazebo GUI | 完整 Gazebo GUI（经 VNC） |
| 本机依赖 | 需装 Gazebo | 仅需 VNC 客户端 |
| 对现有 RDP 影响 | 无 | 间接（GPU 争用） |
| 运维成本 | 低 | 高 |
| 交互延迟 | 低（本机渲染） | 中～高（编码传输） |
| 推荐优先级 | **高** | **低（备选）** |

## 6. 实体显示器 / 本地控制台补充说明

本节说明「给 hxbl 接实体显示器」能否解决 Gazebo GUI 问题，以及与现有 RDP 的关系。

### 6.1 结论（先读）

**接实体显示器可以解决「在服务器本机桌面里开 Gazebo GUI」的问题，但不能让远程 RDP 用户照常弹出 Gazebo 窗口。**

原因：当前故障点是 **GRD 远程桌面的嵌套图形会话**，不是单纯「机器没接显示器」。本机登录 GDM 后使用的是 **直连 GPU 的本地 Wayland/X 会话**（通常对应 `:0` 或主座席），与 RDP 的嵌套 Xwayland 路径不同，OpenGL/EGL 行为也完全不同。

### 6.2 当前机器状态

测试时 `nvidia-smi` 显示 RTX A6000 为 **`Disp.A Off`**，表示 GPU 显示输出未激活。常见原因包括：

- 未接显示器，或仅接在主板视频口而非显卡输出口  
- 使用了无头服务器配置，显示管线未拉起  

在此状态下，部分依赖显示设备的 EGL/GLX 初始化更容易失败；但 **激活显示输出 alone 并不能修复 RDP 内的 Gazebo GUI**。

### 6.3 方案原理

```text
  ┌─────────────────────────────────────────────────────────────┐
  │ hxbl + RTX A6000                                            │
  │                                                             │
  │  实体显示器 ──► GPU 输出口 ──► 本地 GDM 会话 (:0 / 主座席)   │
  │                                    │                        │
  │                                    ▼                        │
  │                         gz sim -r  ✅ 通常可正常显示 GUI     │
  │                                                             │
  │  远程队员 ──► RDP :3389 ──► GRD 嵌套 Wayland/Xwayland       │
  │                                    │                        │
  │                                    ▼                        │
  │                         gz sim -r  ❌ 仍失败（与是否接显示器无关）│
  └─────────────────────────────────────────────────────────────┘
```

### 6.4 三种接法对比

| 接法 | 说明 | 对 Gazebo GUI 的帮助 | 对远程 RDP 队员的帮助 |
| --- | --- | --- | --- |
| **A. 实体显示器 + 键鼠，本机登录** | 到机房在显示器前用 `hazard_*` 账号登录 GNOME | **高**：本机终端 `gz sim -r` 或默认 launch 通常可用 | **无**：远程 RDP 行为不变 |
| **B. HDMI 欺骗器（headless dongle）** | 小插头插在 GPU HDMI/DP 口，骗过 GPU「有显示器」 | **低～中**：`Disp.A On`，利于部分离屏渲染、VirtualGL；**不保证** RDP 内 GUI | **基本无** |
| **C. 显示器仅挂着，队员只用 RDP** | 显示器常亮但无人本地操作 | **无实质帮助** | **无** |

### 6.5 优势

| 优势 | 说明 |
| --- | --- |
| **本机 Gazebo GUI 可靠性高** | 本地 GNOME 会话走标准 NVIDIA 驱动路径，避免 GRD 嵌套会话的 EGL 问题 |
| **实施相对简单** | 一根线、一台显示器即可，无需本机装 Gazebo、无需 VirtualGL |
| **适合平台组现场搭场景** | 调 world、模型、插件时，可直接在服务器上看完整 Gazebo 编辑器 |
| **可与其他方案并存** | 本机调好后，仿真仍可切回 `headless:=true` 供远程队员联调 |
| **激活 GPU 显示输出** | `Disp.A On` 后，有利于 headless rendering、VirtualGL 等依赖显示管线的方案 |
| **无额外远程协议** | 现场操作不增加 VNC 端口或双轨入口 |

### 6.6 问题与限制

| 问题 / 限制 | 说明 |
| --- | --- |
| **不解决远程 RDP 开 GUI** | 全队主要工作方式仍是 RDP 时，接显示器 **不能** 替代 headless 或本机 `gz sim -g` |
| **需要现场到场** | 队员不在机房则无法使用本机 GUI，扩展性差 |
| **单座席并发** | 一台显示器通常对应一个本地登录座席；与多组同时远程 RDP 是不同维度 |
| **账号会话互斥** | 同一 `hazard_*` 若已占 RDP 图形会话，本地登录可能顶掉或复用会话，需先协调断开 RDP |
| **GPU / 座席争用** | 本地有人跑 Gazebo GUI 时仍占 GPU；与多路 RDP 并发时可能加重 `nv_drm_master_set` 竞争 |
| **线缆接错无效** | 线必须接在 **RTX A6000 输出口**，接主板集显口可能仍 `Disp.A Off` |
| **不能替代全队工作流** | 只适合少数人、短时在机房调试，不适合作为默认全队方案 |
| **显示器常开无人在场** | 仅挂显示器不接本地操作，对 RDP 用户几乎无帮助 |

### 6.7 推荐用法（若机房具备条件）

1. 将显示器接到 **A6000** 的 DisplayPort / HDMI 口，确认 `nvidia-smi` 中 **`Disp.A On`**。  
2. 需要调 Gazebo 场景时，**到机房本地登录**对应 `hazard_*` 账号（建议先断开该账号的 RDP）。  
3. 在本机终端运行：
   ```bash
   source /opt/ros/jazzy/setup.bash
   source ~/HazardWalker/ros2_ws/install/setup.bash
   export ROS_DOMAIN_ID=<本组 ID>
   ros2 launch hazardwalker_platform gazebo_minimal.launch.py
   # 或 gz sim -r <world.sdf> -v 2
   ```
4. 场景调好后，切换为 **headless** 供远程联调；或保持 server 运行，远程用 **方案二** `gz sim -g` 连接。  
5. 若仅为了 `Disp.A On`、无人本地看图，可用 **HDMI 欺骗器**（成本低），但不要期望它能修复 RDP 内的 Gazebo GUI。

### 6.8 与其他方案对比

| 维度 | 实体显示器 + 本机登录 | Headless + 本机 `gz sim -g` | 仅接显示器 + RDP |
| --- | --- | --- | --- |
| 本机 Gazebo GUI | ✅ 可靠 | —（GUI 在队员电脑） | ❌ |
| 远程队员看 3D | ❌ 需到场 | ✅ | ❌ |
| 改动现有 RDP | 无 | 无 | 无 |
| 需到场 | 是 | 否 | 否 |
| 推荐优先级 | **中**（机房现场） | **高**（远程） | **不推荐** |

### 6.9 与 VirtualGL 的关系

- VirtualGL 在无显示器时常需 **dummy HDMI** 或实体显示器，使 GPU 显示管线可用。  
- **实体显示器** 解决的是「本机有一个真实可用的显示座席」；**VirtualGL** 解决的是「把该座席上的 OpenGL 画面编码给远程 VNC 用户」。  
- 若已接实体显示器且接受 **仅本机观看**，通常 **不必再上 VirtualGL**；VirtualGL 适合「无人在机房、但要在远程看服务器侧 3D 窗口」的场景。

## 7. 方案选型速查

| 场景 | 推荐方案 |
| --- | --- |
| 日常开发、联调、比赛仿真 | **方案一** Headless |
| 平台组调场景、需完整 Gazebo 3D（远程） | **方案二** 本机 `gz sim -g`（见 [Gazebo远程GUI分离操作指南.md](Gazebo远程GUI分离操作指南_20260706.md)） |
| 导航 / 感知看传感器与位姿 | **方案三** RViz2 |
| 相机仿真出图 | **方案四** Headless Rendering（需实测） |
| 必须服务器侧 3D 且本机无法装 Gazebo | **方案五** VirtualGL + VNC（慎重） |
| 队员在机房现场、需本机 Gazebo GUI 调场景 | **方案六** 实体显示器 + 本地 GDM 登录 |
| 仅为了让 GPU `Disp.A On`、无人本地操作 | HDMI 欺骗器（辅助，不单独作为 GUI 方案） |

## 8. 不建议的做法

| 做法 | 原因 |
| --- | --- |
| 在 RDP 终端直接 `gz sim -r`（不传 headless） | 高概率失败或拖垮远程桌面 |
| 仅升级 NVIDIA 驱动指望解决 | 根因是 RDP 嵌套会话架构，非单一驱动版本问题 |
| 全队用 VirtualGL 替代 RDP | 运维复杂，且与 GRD 争 GPU，得不偿失 |
| 接显示器后指望 RDP 内直接开 Gazebo GUI | 根因是嵌套远程会话，接显示器不能修复 RDP 路径 |
| 放弃 Gazebo 换其他仿真器 | 与项目技术栈不符（若仍要求使用 Gazebo） |
