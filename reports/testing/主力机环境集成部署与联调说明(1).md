# 主力机环境、集成部署与联调说明

更新时间：2026-07-15

适用范围：主力机环境、集成部署、联调问题材料，以及环境稳定性、网络配置、Docker/SimEnv 部署说明。

## 1. 工作范围

本部分主要把 HazardWalker 在主力机 `hxbl` 上的运行环境、账号隔离、网络连接、Docker/SimEnv 部署和联调问题整理成可复用材料，保证各组后续能按统一方式登录、构建、运行和排查。


## 2. 主力机环境

主力机 `hxbl` 当前作为团队集成、仿真、离线测试和高算力实验环境。系统级依赖由环境负责人统一维护，各组使用独立 Linux 账号和独立工作目录，避免构建产物、ROS 话题和 Python 环境互相污染。

核心环境如下：

| 项目 | 当前配置 |
|---|---|
| 系统 | Ubuntu 24.04.x LTS |
| CPU | Intel Core i9-13900K，24 核 / 32 线程 |
| 内存 | 约 94 GiB 可见内存，Swap 8 GiB |
| GPU | NVIDIA RTX A6000，约 48 GB 显存 |
| NVIDIA Driver | 535.309.01 |
| CUDA runtime | 12.2 |
| ROS | ROS 2 Jazzy |
| Gazebo | Gazebo Harmonic / Gazebo Sim 8.x |
| Python | Python 3.12 |
| 构建工具 | colcon、rosdep、pip、venv |

各组账号使用独立目录：

```text
/home/hazard_platform/HazardWalker
/home/hazard_nav/HazardWalker
/home/hazard_perception/HazardWalker
/home/hazard_decision/HazardWalker
/home/hazard_test/HazardWalker
/home/hazard_docs/HazardWalker
```

共享大文件只放入 `/srv/hazardwalker` 下的数据、模型、rosbag 和视频目录；代码仓库、`ros2_ws/build`、`ros2_ws/install`、`ros2_ws/log` 和 Python 虚拟环境不跨用户共享。

## 3. 环境稳定性结论

主力机基础环境已经完成搭建和常规验收，ROS 2、Gazebo、colcon、rosdep、Python、NVIDIA 驱动和基础命令均有明确检查入口。日常验证流程为：

```bash
cd ~/HazardWalker
./scripts/setup_env.sh
python3 scripts/run_offline_tests.py
./scripts/build.sh
./scripts/run_minimal_demo.sh
```

当前稳定性结论：

| 模块 | 结论 |
|---|---|
| 系统基础环境 | Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonic 环境已具备 |
| 独立账号 | 各组 home 目录、ROS 工作空间和构建产物隔离 |
| Python/ROS | 普通离线测试和 ROS 构建默认使用系统 Python，避免 conda/venv 污染 |
| GPU | 驱动可用，GPU 实验需提前报备；普通离线测试不占用 GPU |
| 大文件 | 模型、数据集、rosbag、视频统一放共享目录，不进入 Git |
| 最小 demo | 可作为基础链路验收入口，验证 fake platform、感知、导航、决策和结果输出闭环 |

已知需要注意的稳定性事项：

- 不建议在 PyTorch venv 或 conda 环境中执行 `colcon build` 或 ROS demo。
- Gazebo GUI 不建议直接在 RDP 远程桌面内运行；日常仿真优先使用 headless。
- Docker 权限不默认开放，需要由管理员按需授权。
- 大型依赖、模型权重、官方 SDK、rosbag 和视频下载前需确认保存位置。

## 4. 网络配置与联通性

网络测试已经完成，目前没有已知网络问题。主力机提供两条 SSH 入口：

```text
Tailscale 私网：ssh <账号>@100.102.91.31
公网跳板：    ssh -p 6002 <账号>@47.98.141.33
```

当前网络配置说明：

- Tailscale 私网作为日常优先入口，适合稳定 SSH 开发。
- 公网跳板入口通过反向 SSH 隧道提供备用连接。
- 远程桌面公网访问可通过 SSH 本地端口转发连接到 RDP。
- ROS 2 多组并行运行时使用 `ROS_DOMAIN_ID` 隔离 DDS 通信，避免 `/hw/*` 话题串扰。
- 如有需要可以配置 SSH 公钥。

当前结论：网络侧已按 Tailscale、公网反向 SSH、RDP 隧道和 ROS_DOMAIN_ID 隔离完成配置与测试，日常开发和联调理论上不会成为主要问题。后续只需保持账号、公钥、端口转发和 ROS 域配置一致。

## 5. 集成部署流程

团队内统一使用 `/hw/*` 作为算法侧稳定接口。平台或仿真源可以变化，但导航、感知和决策节点不直接依赖官方 SimEnv、Gazebo 原始话题或 Docker 内部话题。

标准集成流程：

```bash
cd ~/HazardWalker
git fetch origin
git pull
./scripts/setup_env.sh
python3 scripts/run_offline_tests.py
./scripts/build.sh
./scripts/run_minimal_demo.sh
```

运行结果检查：

```bash
ls reports/run_results
python3 scripts/evaluate_result.py reports/run_results/<timestamp>_result.json
```

平台适配原则：

- 本地 Gazebo Harmonic profile 使用 `ros_gz_bridge` 和平台 relay 输出 `/hw/*`。
- 官方 SimEnv 仍以 ROS1 Noetic + Gazebo Classic 为基础，通过适配器桥接到 ROS2 `/hw/*`。
- 业务节点只订阅或发布 `/hw/*`，不直接写死官方话题名。
- fake platform、Gazebo profile、官方 SimEnv adapter 是三种平台入口，不能把某一平台的启动日志当作完整任务闭环证据。

## 6. Docker/SimEnv 部署说明

当前 SimEnv 相关部署采用三目录隔离，避免修改原版 SimEnv：

```text
~/Guoyulun/Competition/
├── SimEnv/          # 原版 ROS1 catkin，仅作只读源或平台组维护源
├── SimEnv_ROS1/     # Docker 版 ROS1，Ubuntu 20.04 + ROS1 Noetic + Gazebo Classic
└── SimEnv_ROS2/     # ROS2 迁移栈，Gazebo Harmonic + HazardWalker /hw/* 联调
```

三层用途：

| 目录 | 入口 | 用途 |
|---|---|---|
| `SimEnv` | `./auto.sh` | 原版源码和 devel，主机 Ubuntu 24.04 下不作为主要运行入口 |
| `SimEnv_ROS1` | `./auto_docker.sh` | Docker ROS1、四足步态、Gazebo Classic、Mid360 |
| `SimEnv_ROS2` | `./auto_ros2.sh` | 日常 HazardWalker 联调、ROS2 迁移和 `/hw/*` 验收 |

Docker ROS1 常用入口：

```bash
cd ~/Guoyulun/Competition/SimEnv_ROS1
./auto_docker.sh build
./auto_docker.sh up
START_CONTROLLER=1 ./auto_docker.sh up
```

ROS2 主链路常用入口：

```bash
export ROS_DOMAIN_ID=20
export GZ_PARTITION=hazardwalker_test
cd ~/Guoyulun/Competition/SimEnv_ROS2
./auto_ros2.sh
./run_simenv_hazardwalker.sh
./verify_ros2_migration.sh
```

现有 Docker/SimEnv 验收信息：

- `SimEnv_ROS2` 已完成场景生成、colcon 构建、`/hw/*` 传感器和基础业务节点验收。
- `SimEnv_ROS1` 与原版 `SimEnv` 已目录分离，避免 Docker 脚本和 ROS2 迁移文件污染原版目录。
- Docker ROS1 源接口已覆盖里程计、IMU、LiDAR、RGB、深度、点云、TF 和 `/cmd_vel`。
- 宿主机 `/hw/*` 桥接接口已有接口测试记录，包含 `/hw/odom`、`/hw/imu`、`/hw/lidar/points`、`/hw/camera/*`、`/hw/tf` 和 `/hw/cmd_vel`。
- 其他 Docker 相关能力仍在运行测试中，可在后续测试完成后补充到同一文档体系。

## 7. 官方 SimEnv ROS1/ROS2 适配

官方 SimEnv 与 HazardWalker 的关系如下：

```text
官方 SimEnv ROS1 / Gazebo Classic
        ↓ rosbridge 或适配器
HazardWalker 稳定 /hw/*
        ↓
ROS2 导航 / 感知 / 决策 / 结果输出
```

核心映射：

| 官方 ROS1 | HazardWalker `/hw/*` | 用途 |
|---|---|---|
| `/Odometry_gazebo` 或 `/hazardwalker/odom` | `/hw/odom` | 里程计 |
| `/real_sense/rgb/image_raw` 或 `/camera/image_raw` | `/hw/camera/image_raw` | RGB 图像 |
| `/real_sense/depth/image_raw` | `/hw/camera/depth_image` | 深度图 |
| RGB/深度 CameraInfo | `/hw/camera/*camera_info` | 相机内参 |
| `/scan`、Livox 点云 | `/hw/lidar/points` | LiDAR / 点云 |
| `/cmd_vel` | `/hw/cmd_vel` | 速度控制 |
| `/tf`、`/tf_static` | 同名或适配后转发 | 坐标变换 |

截至 2026-07-15，官方 SimEnv headless 接入已有验证记录：RGB、深度、内参、`/scan`、`/clock`、里程计均有真实消息进入适配链路；ROS2 `/hw/cmd_vel` 可实际驱动 A1，且已记录前进、转向和停止相关证据。

需要强调的是，这些结果证明官方 SimEnv 与 ROS2 `/hw/*` 链路可用，但不等于完整比赛任务已经闭环。完整闭环仍需要后续验证自主探索、红球搜索、多视角确认、三维定位、返航和最终结果文件输出。

## 8. 联调问题材料

当前联调问题材料按问题类型整理如下：

| 类型 | 现状 | 处理建议 |
|---|---|---|
| 网络连接 | 已测试完成，无已知问题 | 保持 Tailscale、公网 SSH、RDP 隧道和 ROS_DOMAIN_ID 配置一致 |
| Gazebo GUI | RDP 内直接启动 Gazebo GUI 不稳定 | 默认 headless；需要 GUI 时采用 server/client 分离或本地 GUI |
| ROS 域串扰 | 多组并行运行存在话题串扰风险 | 各组固定 `ROS_DOMAIN_ID`，联调时统一指定 |
| Python 环境 | conda/venv 容易影响 ROS 构建 | ROS 构建和 demo 默认使用系统 Python |
| Docker 权限 | Docker 权限等价于高系统权限 | 普通账号按需申请，不默认开放 |
| SimEnv 目录污染 | 原版 SimEnv 不应混入 ROS2/Docker overlay | 使用 `SimEnv`、`SimEnv_ROS1`、`SimEnv_ROS2` 三目录隔离 |
| 控制链路证据 | 单看订阅数或转发计数不够 | 必须结合 `/cmd_vel`、控制器输入和真实 odom 位移 |

Gazebo 远程 GUI 的当前结论是：仿真 server、传感器和 bridge 可正常用于联调，问题主要出在 RDP 嵌套图形会话对 Gazebo 原生 GUI 的支持不稳定。因此默认运行方式应为 headless，必要时再使用 Gazebo server/client 分离或本机图形客户端。
