# diagnostic_13：RGB-D 延迟配对复测被导航卡死阻断

本目录是官方 `auto.sh` 固定 `SEED=2026071802` 随机三层复杂楼宇的真实运行记录，
不是受控专项成绩。运行期只使用公开 RGB、深度、相机内参、雷达、IMU、合法
Cartographer SLAM、公开门控服务和 `/hw/cmd_vel`；未读取场景布局、危险源真值或
Gazebo ground truth。

## 运行结论

- 代码版本：`5d41c9fd0fca8dd5cb64d9d9468cf2cd63e767eb`。
- 本轮加载了“RGB 最多等待一帧，再与随后到达的同时间戳深度配对”的修复，严格
  `20 ms` 同步门槛没有放宽。
- Cartographer 持续建图并保存 `1359 × 1236 @ 0.05 m` 地图；共记录 1494 帧、
  224 条合法 SLAM 轨迹样本。
- Frontier 真实进入复杂楼宇并经过走廊、楼梯口和多个房间入口，但约 80 秒后开始
  在墙边反复选择同一不可达前沿。
- 本轮没有进入红球可见区域，0 帧出现候选。因此既不能证明 RGB-D 延迟配对实景
  生效，也不能据此评价红球召回率。
- 任务未完成、未返航、未生成可提交的 `detected_danger.json`。发现重复卡死模式后
  主动停止隔离试验，避免继续消耗算力；平台组容器未受影响。

## 直接失败原因

`frontier_explorer_node` 检测到卡死后只清空 `current_path` 和 `current_target`，
没有先把当前目标写入短期不可达集合。下一次规划仍按信息增益把同一点选为最佳目标，
形成以下真实循环：

1. 选择约 `(3.88, -3.4)` 的前沿；
2. A1 在墙边无法继续，约 15 秒后触发 stuck；
3. 清空路径；
4. 立即重新选择同一前沿。

日志中该循环连续出现 7 次。总览后半部分也可见镜头在同一组墙角和窄通道附近反复
变化。这是导航联调阻断感知验证，不是“没有红球”或“RGB-D 修复失败”的证据。

## 后续修复

1. EXPLORING 卡死时先将当前前沿按 TTL 标记为不可达，再清空路径，强制尝试其他区域。
2. RETURNING 增加独立无进展看门狗和周期重规划，不能仅在探索状态恢复卡死。
3. 600 秒总预算至少预留 120 秒返航，并按距家距离动态增加返航预算。
4. A* 分离起点与终点吸附半径，返航终点吸附不得大于到家容差。
5. 完成上述回归后，再用同一 SEED 复测 RGB-D 同帧定位和主动多视角确认。
